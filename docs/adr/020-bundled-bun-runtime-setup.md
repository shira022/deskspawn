# ADR-020: bun同梱の実装と初回環境チェック（ADR-011の実装）

## Status
accepted（ADR-011 を実装し、初回展開の方式を「同梱バイナリを直接使う」に改める）

> 実装は分割して着地させる。本ADRのうち **1・2項（同梱と解決順）は先行PR**、
> **3・4項（初回環境チェックUIと限定IPC）は後続PR** で実装する。

## Context

ADR-011 は「bun.exe をアプリに同梱し、初回起動時に `~/deskspawn/tools/bun/` へ展開する」と
決定していたが、**実装は存在しなかった**（リポジトリ内に展開コードは無く、sidecar の解決順は
`BUN_PATH` → `PATH` → 開発用レイアウトの3段階のみ）。その結果、配布ビルドは
**ユーザーのPCに bun が入っていることを暗黙の前提**にしていた。

この状態で非エンジニアのユーザーが最初に遭遇するのは、次のような体験である。

- 生成は成功するが、プレビュー開始時に `Bun 実行ファイルが見つかりません…` という
  エラー文字列だけが出る（何をすればよいか分からない）。
- 旧 `EnvCheckScreen`（未導入ツールの一覧＋wingetワンクリック導入UI）は 2026-06 に削除済みで、
  i18n の `env.*`（ja/en 28キー）と Rust の `check_environment`（Node.js のみ判定）/
  `check_winget` が**未使用の残骸**として残っているだけ。
- 導入実行側の IPC `install_with_winget` は、任意パッケージを実行できるRCE面として
  セキュリティ監査で削除済み（安易に元へ戻せない）。

さらに winget の `Oven-sh.Bun` は **portable(zip) インストーラ**で、
`%LOCALAPPDATA%\Microsoft\WinGet\Links` にリンクを作る方式のため、
**インストール直後に起動中のアプリプロセスの PATH へは反映されない**（再起動が必要になる）。

## Decision

1. **bun.exe を Tauri の `externalBin` として同梱する。**
   ビルド時に `scripts/fetch-bun.mjs` がピン留めしたバージョン（1.3.14）の公式zipを取得し、
   SHA256 を検証して `src-tauri/binaries/bun-<target-triple>[.exe]` に配置する
   （`binaries/` は .gitignore 済み。取得は冪等で、`--check` で存在検証のみ可能）。
2. **実行時の解決順を一本化する**: `BUN_PATH` → 同梱（実行ファイルと同階層）→ `PATH` →
   `~/.bun/bin` → winget Links → 開発用レイアウト。解決は **Rust が行い、sidecar 起動時に
   `BUN_PATH` として渡す**（winget の PATH 反映ラグを待たずに動作する）。
3. **初回起動に環境チェック画面を置く（デスクトップのみ）**。一覧に出すのは
   **bun と WebView2 の2つだけ**とし、ビルド専用ツール（Node.js / pnpm / rustup /
   VS Build Tools）は**表示しない**（利用者に不要な不安を与え、実際には使わないため）。
   順序は「言語選択 → 環境チェック → AI設定 → メイン」で、全項目OKなら自動で次へ進む。
4. **winget による導入はフォールバック**（同梱が見つからない/壊れている場合のみ）。
   IPC は `kind` を **enum（bun | webview2）に限定**し、パッケージIDはRust内の定数、
   シェル経由なしの固定引数配列で実行する。**任意パッケージを指定できるIPCは復活させない**。
5. 画面文言は既存の i18n `env.*` を再利用し、ja/en 両方を揃える。検出結果には
   「同梱 / PATH / 見つからない」の由来を出し、導入失敗時は手動リンクとコピー可能な
   コマンドを提示する。

## Alternatives Considered

- **winget のみ（同梱しない）**: インストーラサイズは増えないが、初回に約100MBのDL・
  ネットワーク必須・数十秒待ち・PATH反映ラグの考慮が必要で、非エンジニアの初回体験として弱い。
- **ADR-011 の「初回起動時に `~/deskspawn/tools/bun/` へ展開」**: 展開失敗時の復旧経路と
  ディスク二重消費（同梱分＋展開分）が増える。同梱バイナリをそのまま実行すれば足りるため採用しない。
- **PATH への追加のみ（現在の挙動）**: そもそも bun が無い環境では成立しない。
- **旧 `install_with_winget` の復活（任意パッケージ）**: 任意コード実行面になるため却下（4項の限定IPCで代替）。
- **生成アプリのプレビューを bun 非依存にする**: 生成物が `bun install` / `bun run dev` を
  前提にしており、置き換えは別ADR級の設計変更になる。

## Consequences

- **初回体験**: ユーザーは何もインストールせずにプレビューまで到達できる（オフラインでも可）。
- **サイズ**: インストーラが約40MB増える（bun.exe 約98MB・圧縮後）。MSIX/MSI/NSIS いずれも同様。
- **更新**: 同梱bunの更新はリリース毎のバージョンピン変更＋`fetch-bun.mjs` のハッシュ更新で行う。
- **セキュリティ**: 新設する導入IPCは kind 列挙のみで、パッケージID・引数はコード側で固定。
  実行者は winget のみ。UIからの任意文字列が実行系に渡る経路を作らない。
- **保守**: `BUN_PATH` を Rust が渡すため、sidecar 側の解決ロジックは「Web/dev 実行時の
  フォールバック」に限定される（二重実装ではなく優先順位の違う保険）。
- **未対応**: Web版（評価用）には影響しない。macOS配布は署名の都合で未提供のまま。
